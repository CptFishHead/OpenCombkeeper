# Требования OpenCombkeeper MVP

## Цель

1. Получить хотя бы одну единицу каждого доступного вида сот.
2. В режиме `best` сохранить по одной живой линии лучших доступных производителей.
3. Один вид пчелы может закрывать несколько продуктов; один продукт не создаёт несколько целей.
4. Лучший производитель определяется максимальным базовым шансом продукции. При равенстве выбираются меньшая глубина мутации, меньше условий и стабильный UID.

## Планирование

5. До старта показать достижимые и недостижимые соты, выбранных производителей, стартовые принцессы, мутации и ручные задачи.
6. Дроны базовых видов считаются доступными. Дроны полученного вида считаются воспроизводимыми после первого цикла его линии.
7. Количество принцесс — детерминированное безопасное число для выбранного плана без потерь. Оно не выдаётся за гарантию при Genetic Waste.
8. Планировщик не должен считать случайное выпадение сот детерминированным. Для оценки используется задаваемая вероятность успеха.
9. Однозначность мутации определяется по неупорядоченной паре родителей среди доступных рецептов.

## Исполнение

10. Принцесса учитывается как логическая линия. NBT используется для проверки вида/типа, но не как постоянный ID линии.
11. Промежуточные родители проходят стандартный импринтер перед разведением.
12. Однозначные мутации выполняются обычным мутатронам автоматически.
13. Неоднозначные мутации создают задачу игроку для продвинутого мутатрона.
14. Игрок возвращает результат ручной мутации в выделенный пустой контейнер импорта и запускает проверку задачи. Непустой контейнер блокирует старт ручной задачи.
15. Если финальный производитель уже выдан, но его дрон нужен дальше, создаётся отдельная задача игроку.
16. Финальные производители выдаются в отдельный сундук и не используются в рискованных операциях.
17. `restore` через чужого родителя отсутствует. Потеря линии расходует резерв либо останавливает план с точным дефицитом.
18. Состояние линии, операции и ручной задачи сохраняется до физического действия.

## Топология

19. При первом `run` отсутствие топологии запускает мастер bind; выбор «первого» компонента без проверки запрещён.
20. МЭ-интерфейс сопоставляется с транспозером проверочным предметом, а не порядком UUID.
21. Предыдущая топология заменяется только после полной успешной привязки и атомарной проверки записи.
22. Каждый старт проверяет сохранённые адреса, стороны и типы устройств без перемещения предметов.
23. Временная недоступность компонента, занятый буфер и подтверждённое изменение оборудования показываются как разные состояния.
24. Повторный bind выполняется только по выбору игрока; прерванный запрос имеет отдельное восстановление `bind-reset`.
25. Контейнер ручного результата может содержать ожидаемую матку при старте `check`; требование пустоты применяется перед активацией новой ручной задачи.

## Ограничения MVP

- Клиентские вероятности и рецепты могут отличаться от сервера.
- Точное время зависит от механизмов, доставки и случайной продукции.
- Планировщик минимизирует очевидные локальные метрики и не обещает глобальный математический оптимум гиперграфа.
