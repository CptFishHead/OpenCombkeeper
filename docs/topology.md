# Привязка оборудования

Команды намеренно совпадают по модели с OpenBeekeeper:

| Команда | Действие |
|---|---|
| `opencombkeeper scan` | Только перечисляет компоненты и соседние инвентари |
| `opencombkeeper bind` | Создаёт полную топологию |
| `opencombkeeper rebind` | Явный синоним повторной привязки |
| `opencombkeeper bind-reset` | Снимает запрос после прерванного bind |
| `opencombkeeper topology` | Показывает сохранённые модули и роли |
| `opencombkeeper topology-check` | Проверяет только топологию без перемещений |
| `opencombkeeper check` | Проверяет топологию и результаты активных ручных задач |

## Первый запуск

Если файла `/home/.opencombkeeper-data/topology` нет, обычный `run` запускает bind.
Каждый транспозер с рабочими инвентарями и ровно одним соседним МЭ-интерфейсом
становится кандидатом модуля. Компоненты интерфейсов нельзя сопоставлять с ними по
порядку UUID, поэтому программа по очереди запрашивает один булыжник и наблюдает,
в каком локальном буфере он появился.

Мутатроны и импринтеры получают роли по имени инвентаря. Для трёх обычных
контейнеров игрок выбирает роли вручную. Один контейнер нельзя назначить двум
ролям.

## Безопасность

До изменения интерфейса программа записывает `bind-pending`. При ошибке запрос
снимается до очистки временного дескриптора базы. Незавершённый журнал блокирует
новый bind и восстанавливается командой `bind-reset`.

Занятые конфигурационные слоты чужих интерфейсов не очищаются: такие интерфейсы
пропускаются. Буферы кандидатов должны быть пустыми. Частичная новая карта не
заменяет рабочую старую карту.

Повреждённый файл топологии не считается отсутствующим и не перезаписывается
автоматически. Сообщение указывает сохранить его для диагностики; новую карту
можно создать только явным `rebind`.
